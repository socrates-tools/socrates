# 3.1: the socrates-implement skill teaches the overseer

## What to build

`socrates implement skill` also installs the `socrates-implement` skill, under the skills directory or `--to`, a person's only, so a person who invokes it gets an overseer that lands the change's tickets without writing code.
The skill states the overseer's whole loop as the spec does:

- Read the main ticket, the spec and the ADRs, and read the settings with `socrates implement config` at the start of every run.
- Where no default branch is remembered, propose the repository's branches named `main`, `master`, `dev` or `develop`, never one under a prefix such as `feature/` or `hotfix/`, ask in the terminal, and save the answer with `socrates implement default-branch`.
- Start only from a working tree whose uncommitted changes are what the design and the tickets left, and make those the first commit of a branch named for the change, cut from the current `HEAD`.
- The frontier is every ticket whose blockers are done; run at most `concurrency` implementers, the longest chain waiting behind a ticket first, then the most it unblocks, then name order; hold back a ready ticket sharing a surface with a running one, and write no blocker.
- Make each implementer's worktree and branch with git off the change's branch, brief it with pointers rather than paraphrase, and run it in the background so the overseer stays free to talk to the person.
- Review each diff against the ticket, the spec and the ADRs, send feedback to the same implementer with no cap, and hand a stalled ticket to a fresh one where her judgement says so.
- Land by fast-forward, run the repository's own verification on the change's branch after every landing, and send a failure back to the implementer whose ticket landed last.
- Commit in progress before a hand-out and done once a ticket has landed and passed; a resumed overseer continues each in-progress ticket from its own branch with a fresh implementer.
- Relay what the person says mid-run at once to every implementer it concerns, and reach the person in the terminal only about what coding cannot fix.
- Once the last ticket lands, read the whole change against the spec from the fork point of the default branch, hand what falls short to one implementer, remove every worktree, say the branch is ready, and push nothing.

The README explains the namespace where it explains design.
