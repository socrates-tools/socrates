# 3.4: The overseer runs on Codex

## What to build

A person who types `$socrates-implement` in Codex gets an overseer that builds a change's tickets through Codex subagents, each in a worktree the overseer made, while it stays free to talk to them.
Before handing anything out it checks that Codex's sandbox lets it write socrates implement's directory, and where it does not it says what grants that and starts nothing.

## Acceptance criteria

- [ ] The Codex rendering tells the overseer to spawn each implementer with `spawn_agent` naming `agent_type` `socrates-implementer`, to send feedback with `send_input`, to collect reports with `wait_agent` between answering the person, and to close each implementer with `close_agent` once its ticket has landed.
- [ ] It tells the overseer to check at the start of every run that it can write the directory beside the file `socrates implement config` prints on its first line, and where it cannot, to start nothing and name `writable_roots` under `[sandbox_workspace_write]` and `--add-dir` with that directory.
- [ ] Where `socrates-implementer` is not a role it can spawn, it tells the person to run `socrates implement skill` and starts nothing.
- [ ] Every other promise of the overseer holds in the Codex rendering as in Claude Code's, and implement's instruction file states which differ per host.
- [ ] The rendering stays within its ceiling.
